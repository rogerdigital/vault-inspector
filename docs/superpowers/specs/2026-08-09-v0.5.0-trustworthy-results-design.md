# Vault Inspector 0.5.0 Trustworthy Results Design

## Summary

Vault Inspector 0.5.0 will turn the plugin's current issue list into a
verifiable maintenance loop:

```text
detect -> explain -> act -> rescan -> verify
```

The release will improve four related weaknesses together:

- separate finding certainty from impact severity so heuristic findings are not
  presented as proven problems;
- explain the evidence, known caveats, and next action for every finding;
- compare a successful scan with the previous successful scan made with the
  same detection settings;
- report the real result of fixes, ignores, and scanner exclusions instead of
  reducing them to a generic success notice.

The Obsidian plugin is the primary 0.5.0 experience. Shared result metadata and
pure comparison logic remain reusable by the CLI, but the CLI will not gain an
automatic snapshot store or a full scan-history interface in this release.

## Product Goal

After a scan, a user should be able to answer these questions without reading
scanner implementation details:

1. Which findings are new, which still exist, and which disappeared?
2. Which findings are directly proven and which require human judgment?
3. What evidence caused each finding to be reported?
4. What should the user do next, and what exceptions should they consider?
5. Did an attempted action actually remove the finding?

The goal is not to report more issues. It is to make existing findings easier
to trust, review, and resolve.

## Goals

- Preserve the existing eight-scanner product boundary.
- Add a certainty classification that is independent from severity.
- Give every finding a consistent explanation contract.
- Compare only against the previous successful scan with the same detection
  profile.
- Preserve ignored findings in lifecycle comparison so ignoring is not
  misreported as resolution.
- Verify mutation fixes with a post-action scan.
- Expose per-item outcomes for batch operations.
- Connect issue cards to the existing per-scanner ignored-folder setting.
- Migrate existing flat plugin data without losing settings.
- Keep existing CLI stable fields, baseline behavior, and exit codes compatible.

## Non-goals

0.5.0 will not add:

- new scanners;
- multi-scan history, trends, charts, or arbitrary snapshot selection;
- CLI fix execution;
- automatic cleanup or repair without confirmation;
- a general-purpose ignore-rule editor;
- cloud storage, synchronization, accounts, or telemetry;
- UI localization or an i18n framework;
- unrelated scanner or report architecture refactors.

## Finding Semantics

### Severity and classification

`IssueSeverity` continues to express impact:

- `error`: a finding likely blocks a valid vault outcome;
- `warning`: a finding deserves review or maintenance;
- `info`: a finding is informational or low urgency.

A new `FindingClassification` expresses how conclusive the detection is:

```ts
export type FindingClassification =
	| "confirmed"
	| "candidate"
	| "unverified";
```

- `confirmed`: the scanner can prove the stated condition within its documented
  scan boundary. This does not mean the user must fix it.
- `candidate`: the evidence suggests a maintenance problem, but known blind
  spots or intentional workflows can change the conclusion.
- `unverified`: the scanner could not complete the check because required
  information was unavailable, blocked, or timed out.

Severity and classification must not be derived from one another. A confirmed
large file can remain a warning; an unverified external link can remain info.

### Explanation contract

Every issue will provide a structured explanation:

```ts
export type FindingExplanation = {
	why: string;
	caveat?: string;
	nextStep: string;
};
```

`Issue.title` and `Issue.message` continue to state what was found.
`Issue.evidence` continues to carry stable machine-readable facts. The new
explanation tells a person how to interpret those facts.

The fields have these requirements:

- `why` describes the exact detection condition, not a generic scanner summary;
- `caveat`, when present, names a realistic reason the finding may be expected;
- `nextStep` recommends review, configuration, ignore, or a safe available fix;
- no field may claim that a heuristic finding is certainly broken;
- paths, URLs, properties, and tags remain in structured evidence rather than
  being available only inside prose.

### Initial scanner classification policy

The initial mapping is explicit so implementations and tests do not invent
different meanings:

| Scanner | Finding | Classification |
| --- | --- | --- |
| Broken links | unresolved target or missing heading | `confirmed` |
| Orphan attachments | no reference found in the scanned Markdown boundary | `candidate` |
| Empty notes | below the meaningful-content threshold | `candidate` |
| External links | HTTP error status received | `candidate` |
| External links | timeout, request failure, or blocked destination | `unverified` |
| Duplicate files | content hash is identical | `confirmed` |
| Duplicate files | same-name or same-size candidate without hash proof | `candidate` |
| Frontmatter types | incompatible observed value types | `confirmed` |
| Frontmatter types | date-like string ambiguity | `candidate` |
| Tag usage | configured tag missing or below the configured count | `confirmed` |
| Large files | observed size exceeds the configured threshold | `confirmed` |

Every candidate or unverified variant must document its detection boundary in
`caveat`. Confirmed variants include a caveat when the observed condition is
proven but the correct user action can still depend on workflow. For example,
orphan attachments can be referenced by CSS, Canvas, Dataview, publishing
pipelines, or external tools that the scanner does not inspect.

## Scan Profile

Lifecycle comparison is valid only when both scans use the same detection
configuration. A `ScanProfile` will be computed from canonical serialized
settings and represented by a deterministic signature.

The profile includes:

- enabled scanners;
- global ignored folders;
- per-scanner ignored folders;
- large Markdown and attachment thresholds;
- ignored large-Markdown frontmatter keys and path patterns;
- duplicate hash size cap;
- low-usage tag threshold and watched tags;
- empty-note word threshold;
- ignored frontmatter properties.

The profile excludes settings that do not change detection:

- ignored issue fingerprints;
- fix-action enablement;
- duplicate keep mode;
- report folder path;
- report filters and expanded/collapsed UI state.

Object keys are serialized in stable order. Set-like arrays are normalized,
deduplicated, and sorted before signing so reordering an unchanged setting does
not reset comparison.

When the current profile does not match the stored snapshot profile, the plugin
must show that comparison is unavailable because scan settings changed. It must
not label every finding as new. The successful current scan then becomes the
snapshot for the new profile. Only one snapshot is retained.

## Snapshot Model and Persistence

### Snapshot data

The plugin stores a minimal successful-scan snapshot:

```ts
export type ScanSnapshot = {
	schemaVersion: 1;
	comparisonVersion: 1;
	toolVersion: string;
	createdAt: number;
	scanProfile: string;
	issues: SnapshotIssue[];
};

export type SnapshotIssue = {
	fingerprint: string;
	scannerId: ScannerId;
	severity: IssueSeverity;
	classification: FindingClassification;
	title: string;
	message: string;
	primaryPath?: string;
	relatedPaths: string[];
	evidence: Record<string, string | number | boolean>;
	explanation: FindingExplanation;
	ignored: boolean;
};
```

The snapshot stores no note body, attachment content, HTTP response body, or
action history. Its issue data is sufficient to render a resolved item after
the source finding has disappeared.

`schemaVersion` controls persistence compatibility. `comparisonVersion`
controls detection-semantic compatibility and must be incremented when a
scanner or fingerprint change would make before/after states misleading. UI,
documentation, and other non-detection releases do not increment it. Lifecycle
comparison requires matching comparison versions as well as matching profiles.

Both active and ignored findings are included. The `ignored` field records the
previous presentation state but does not change fingerprint comparison.

### Plugin data migration

Plugin persistence will move from flat settings to an envelope:

```ts
export type PersistedPluginData = {
	settings: InspectorSettings;
	lastSuccessfulSnapshot?: ScanSnapshot;
};
```

Loading follows these rules:

1. If the loaded object has a valid `settings` object, read the envelope.
2. Otherwise, treat the loaded object as legacy flat settings.
3. Merge settings with current defaults, including nested scanner maps.
4. Validate the snapshot schema and discard only the snapshot if it is invalid.
5. Save in envelope form on the next settings or snapshot write.

Settings writes and snapshot writes must share one data-store boundary so
changing a setting cannot accidentally erase the snapshot and completing a scan
cannot restore stale settings.

### Snapshot replacement

A snapshot is replaced only after every enabled scanner completes and the scan
result is accepted by the view. A thrown scanner error, cancelled plugin
unload, or incomplete scan leaves the previous snapshot untouched.

Corrupt or unsupported snapshots are ignored without blocking scanning. The UI
shows comparison as unavailable for that scan; it does not show an alarming
vault-health error for a recoverable cache problem.

## Result Comparison

Comparison is implemented as a pure, linear-time operation over fingerprint
maps. It does not reread vault files.

```ts
export type CurrentFindingStatus = "new" | "persisting";

export type ComparedIssue = {
	issue: Issue;
	status: CurrentFindingStatus;
};

export type ResolvedIssue = {
	issue: SnapshotIssue;
	status: "resolved";
};
```

For matching profiles:

- current fingerprint absent from the snapshot -> `new`;
- current fingerprint present in the snapshot -> `persisting`;
- snapshot fingerprint absent from all current active and ignored findings ->
  `resolved`.

Moving a finding between active and ignored states never resolves it. Restoring
an ignored finding never makes it new. A truly disappeared ignored finding is
removed from the ignored section but is not included in the headline resolved
count, which remains focused on findings that previously required attention.

The current scan result remains the source of truth. Snapshot titles and
evidence are used only for resolved items.

## Plugin Experience

### Summary and filtering

The completed-scan summary displays:

```text
Active 42    New 3    Persisting 39    Resolved 7
```

`Active`, `New`, and `Persisting` count non-ignored current findings. `Resolved`
counts findings that were active in the previous snapshot and are absent from
all current active and ignored findings. The existing ignored section retains
its own count.

When comparison is unavailable, the summary displays active and ignored counts
plus a concise reason instead of zero or misleading delta counts.

The existing scanner and severity filters remain. Two filters are added:

- lifecycle status: all, new, persisting;
- classification: all, confirmed, candidate, unverified.

Resolved findings live in a separate collapsed section and are not selectable
for mutation or ignore actions.

### Default ordering

Active findings are ordered by:

1. new confirmed errors;
2. new confirmed warnings;
3. other new confirmed findings;
4. persisting confirmed findings;
5. candidate findings;
6. unverified findings.

Existing stable path or scanner ordering breaks ties. Filtering never changes
the underlying snapshot or status.

### Issue presentation

Every issue card answers four questions:

- **What:** the existing title and concise message;
- **Why:** the explanation and primary structured evidence;
- **Caveat:** known reasons to review before acting;
- **Next:** the recommended next action.

The most important one or two evidence values are visible by default. Remaining
machine-readable evidence is available through a disclosure control. Evidence
must remain selectable and copyable.

### Contextual false-positive handling

Issue cards offer only existing, reversible scope controls:

- ignore this fingerprint;
- exclude the issue's parent folder from this scanner;
- open the scanner's settings.

Folder exclusion is unavailable when the issue has no unambiguous vault path or
parent folder. Before adding an exclusion, the confirmation shows the folder,
scanner, and number of currently visible findings affected. The exclusion is
written to `ignoredFoldersByScanner`, followed by a scan.

Because adding an exclusion changes the scan profile, those findings are
reported as excluded by the action feedback, not as resolved by snapshot diff.
The UI links to settings so the exclusion can be removed.

No file-extension, regular-expression, evidence-field, or compound rule builder
is introduced.

## Action Feedback and Verification

### Mutation fixes

Existing confirmation and fresh-fingerprint checks remain mandatory. Batch
execution records an outcome for every requested issue:

```ts
export type ActionOutcome = {
	fingerprint: string;
	outcome: "fixed" | "still-present" | "skipped" | "failed";
	message: string;
	affectedPaths: string[];
	phase?: "preflight" | "execution" | "verification";
};
```

- `fixed`: execution succeeded and the final verification scan no longer finds
  the fingerprint;
- `still-present`: execution ran, but the final scan still finds the issue;
- `skipped`: fresh evidence no longer matches the confirmed request, so no
  mutation was attempted;
- `failed`: execution or the verification scan failed; `phase` and `message`
  identify where and why.

Individual exceptions are no longer swallowed. The batch summary reports each
outcome count and exposes the associated paths. A final verification scan is
required before any item is called fixed.

### Ignore, restore, and exclusion outcomes

Non-mutation disposition changes use a separate result so they are not
misrepresented as fixes:

```ts
export type DispositionOutcome = {
	fingerprint?: string;
	outcome: "ignored" | "restored" | "excluded" | "failed";
	message: string;
	affectedPaths: string[];
};
```

Ignoring an issue moves it to the ignored section after rescan; it does not
produce a resolved lifecycle state. Excluding a folder reports the scanner and
folder affected. Failures preserve the prior settings or ignored state whenever
possible and provide a recovery path.

## CLI Compatibility

All scanners populate classification and explanation, so CLI JSON and Markdown
outputs receive the new metadata. This is an additive protocol change:

- existing stable top-level and issue fields remain unchanged;
- existing `schemaVersion`, baseline `isNew`, `summary.newIssues`, and exit-code
  behavior remain unchanged;
- consumers that ignore unknown fields continue to work;
- Markdown output includes the explanation without adding plugin lifecycle UI;
- CLI does not automatically read or write plugin snapshots;
- CLI does not emit resolved findings in 0.5.0;
- `--fix` remains reserved and fails without mutating files.

If implementation reveals that an existing stable field must change meaning or
type, that change is outside this design and requires a separate protocol
version decision before implementation continues.

## Components

The implementation should preserve current boundaries and add focused modules:

```text
src/scanner/
  finding-presentation.ts   classification and explanation contracts/helpers
  scan-profile.ts           canonical detection-profile signature
  result-diff.ts            pure lifecycle comparison

src/snapshot/
  scan-snapshot.ts          snapshot types, validation, and legacy migration

src/report/
  render-evidence.ts        consistent explanation/evidence presentation
  render-changes.ts         lifecycle summary and resolved section
```

Scanner-specific classification and prose remain with each scanner or its
focused presentation helper. Snapshot persistence is coordinated by the plugin
entry/data-store boundary. Report modules consume compared results but do not
perform persistence or scanner work.

## Error Handling

- Scanner failure: retain the previous snapshot and show the existing scan
  failure notice.
- Snapshot parse or schema failure: ignore the snapshot, keep settings, and run
  without comparison.
- Profile mismatch: run normally, explain why comparison is unavailable, and
  replace the snapshot only after success.
- Settings save failure: report the failure and do not claim an ignore or
  exclusion succeeded.
- Fix preflight mismatch: skip mutation and report `skipped`.
- Fix execution failure: continue independent batch items and retain the error
  as a per-item `failed` outcome.
- Verification failure: do not call any action fixed; report the verification
  phase failure.
- Missing path for contextual exclusion: hide or disable the action with a
  reason; never infer a broad root exclusion.

## Testing Strategy

### Scanner contract tests

Every scanner test suite will assert:

- the expected classification for each finding variant;
- non-empty `why` and `nextStep` values;
- caveats for known heuristic or incomplete scan boundaries;
- unchanged deterministic fingerprints for existing evidence.

Classification work must not silently change severity or detection behavior.
Any detection correction requires a focused regression test in that scanner's
own commit.

### Profile and comparison tests

Pure unit tests cover:

- stable signatures across key and set-like array reorderings;
- signature changes for every detection-affecting setting;
- no signature changes for UI, fix, report, or ignored-fingerprint settings;
- first scan and profile mismatch behavior;
- comparison-version mismatch behavior;
- new, persisting, and resolved fingerprints;
- active-to-ignored and ignored-to-active transitions;
- previously ignored findings that truly disappear;
- duplicate fingerprint defense and deterministic result ordering;
- large synthetic result sets without nested issue comparison.

### Persistence tests

Tests cover:

- legacy flat-settings migration;
- current envelope loading;
- partial nested settings merged with defaults;
- invalid snapshot discarded without settings loss;
- settings writes retaining the snapshot;
- snapshot writes retaining current settings;
- failed and incomplete scans retaining the previous snapshot.

### Report and interaction tests

DOM-level tests cover:

- summary counts with and without a comparable snapshot;
- lifecycle and classification filters combined with existing filters;
- default ordering;
- evidence disclosure;
- resolved items being non-actionable;
- ignore and restore remaining distinct from resolution;
- contextual folder-exclusion confirmation and settings update;
- per-item batch outcomes and visible failure details.

### Compatibility and release verification

Before release, run:

```bash
npm run lint
npm run lint:obsidian-warnings
npm run build
npm test
npm run test:coverage
npm pack --dry-run
```

Also verify:

- an existing 0.4.x `data.json` upgrades without settings loss;
- plugin scan, ignore, restore, exclusion, fix, and export flows in Obsidian;
- CLI JSON consumers can still read all previously stable fields;
- CLI baseline and exit-code fixtures remain unchanged;
- GitHub release assets remain `main.js`, `manifest.json`, and `styles.css`;
- the npm package still includes `cli.js` and the Agent Skill documentation is
  updated for the new interpretation fields.

## Delivery Plan

Implementation should be delivered in five reviewable stages:

1. finding semantics and per-scanner contract tests;
2. scan profile, snapshot persistence, migration, and result comparison;
3. lifecycle summary, filters, evidence rendering, and resolved section;
4. contextual exclusions and verified per-item action outcomes;
5. compatibility verification, documentation, screenshots, and 0.5.0 release
   preparation.

Scanner changes remain separated by scanner when they alter detection or
severity behavior. Shared type-only migrations may be grouped when all scanner
tests are updated atomically and the intermediate repository cannot compile
otherwise.

## Acceptance Criteria

0.5.0 is ready when:

- every emitted issue has a tested classification and explanation;
- every current issue can explain what was found, why, a relevant caveat when
  needed, and the next action;
- two successful same-profile scans correctly distinguish new, persisting, and
  resolved findings;
- ignored findings that still exist are never marked resolved;
- profile changes, failed scans, and corrupt snapshots never produce false
  comparison states or overwrite a valid snapshot prematurely;
- batch operations expose every requested item's outcome and never swallow an
  exception;
- a mutation is called fixed only after verification no longer finds its
  fingerprint;
- legacy settings migrate without data loss;
- CLI stable fields, baseline behavior, and exit codes remain compatible;
- all repository verification and packaging checks pass;
- no non-goal feature is required to ship the release.
